# moonbit-csv 设计分析

## 1. 设计目标

第一版设计遵循四个原则：

- 简单：优先覆盖最常见 CSV 使用场景
- 清晰：模块边界和错误语义明确
- 稳定：避免过度灵活导致行为不可控
- 可扩展：为后续配置项和高级 API 预留空间

## 2. 设计范围

第一版聚焦“字符串级 CSV 解析与编码”。

包含：

- 解析字符串到记录
- 编码记录到字符串
- 可选表头支持
- 基础错误处理

不包含：

- 文件系统封装
- 流式读取器
- 自动推断数值、布尔、日期等类型

## 3. 推荐模块划分

建议按以下方式拆分：

### `csv`

对外导出公共 API。

职责：

- 暴露 `parse`、`stringify` 等入口
- 组织对外类型定义

### `parser`

实现状态机解析逻辑。

职责：

- 扫描字符流
- 处理字段结束、行结束、引号状态切换
- 构造最终记录结构

### `writer`

实现 CSV 编码逻辑。

职责：

- 判断字段是否需要引号
- 处理双引号转义
- 拼接分隔符和换行符

### `types`

存放公共类型和配置。

建议类型：

- `ParseOptions`
- `WriteOptions`
- `CsvError`
- `CsvDocument` 或 `CsvResult`

## 4. 数据模型建议

### 4.1 基础记录模型

第一版建议直接使用：

- 一行：`Array[String]`
- 全量记录：`Array[Array[String]]`

优点：

- 简单直接
- 容易测试
- 容易与业务层适配

### 4.2 表头模型

可以额外提供：

- `headers : Array[String]`
- `rows : Array[Array[String]]`

或通过辅助函数将二维数组转换为“表头 + 数据行”结构。

第一版不建议直接引入复杂字典模型作为核心返回值，因为：

- CSV 本质上是位置型数据
- 字典模型会引入重复列名、缺列、空列等额外问题

## 5. 解析策略

推荐采用显式状态机，而不是依赖复杂正则或一次性拆分。

核心状态可抽象为：

- `StartField`：准备读取字段
- `InField`：读取普通字段
- `InQuotedField`：读取引号字段
- `AfterQuote`：刚读完一个引号，判断是转义还是字段结束
- `EndRecord`：完成一行

这种设计的优势：

- 容易处理 CSV 的核心难点
- 容易定位边界错误
- 容易写覆盖完整的测试

## 6. 编码策略

写出时可采用以下规则：

- 字段中不含特殊字符时，原样输出
- 字段中包含分隔符、引号或换行时，整体加双引号
- 字段内部的 `"` 编码为 `""`

该策略简单、可预测，且符合常见 CSV 兼容行为。

## 7. 错误设计

建议错误至少覆盖以下几类：

- 未闭合引号
- 非法引号结束状态
- 列数不一致
- 非法输入参数

如果 MoonBit 类型系统允许，优先使用结构化错误而不是只返回字符串。

建议错误信息包含：

- 错误类型
- 行号
- 列号
- 简短说明

## 8. 配置设计

### `ParseOptions`

建议包含：

- `delimiter`
- `has_header`
- `strict_column_count`
- `trim_trailing_empty_lines`

### `WriteOptions`

建议包含：

- `delimiter`
- `line_ending`
- `always_quote`
- `include_header`

第一版配置项数量不要太多，避免实现膨胀。

## 9. API 草案

这里只给出设计层面的接口方向，不绑定具体语法细节。

### 基础 API

- `parse(input)`
- `parse_with(input, options)`
- `stringify(rows)`
- `stringify_with(rows, options)`

### 辅助 API

- `parse_table(input, options)`
- `validate(input, options)`

### 设计取舍

第一版建议把：

- “通用读写 API” 作为主能力
- “表头辅助 API” 作为轻量增强

不要一开始就扩展太多高级方法。

## 10. 测试设计

测试应至少覆盖：

- 正常多行多列解析
- 引号字段解析
- 嵌入逗号解析
- 嵌入换行解析
- 双引号转义
- 空字段
- 尾部分隔符
- `\\n` 与 `\\r\\n`
- 非法输入报错
- 解析后再编码的往返一致性

建议测试分层：

- 单元测试：单个边界行为
- 组合测试：多个 CSV 特性同时出现
- 回归测试：修复过的 bug 保留样例

## 11. 示例设计

比赛和生态展示都需要一个“看得见”的示例。

建议最少提供两个：

- 基础读写示例
- 带表头示例

如果时间允许，可增加：

- 配置化分隔符示例

## 12. 版本规划

### v0.1.0

- 基础解析
- 基础编码
- 错误处理
- 核心测试
- README 和示例

### v0.2.0

- 表头辅助 API
- 严格列数校验
- 更多配置项

### v0.3.0

- 更丰富的错误定位
- 更强的兼容模式

## 13. 结论

`moonbit-csv` 最合适的实现路径是：以小而稳的核心状态机为基础，围绕“解析、编码、错误、测试、示例”建立完整交付。这样既方便比赛验收，也能为后续扩展留下足够空间。
